# タスク：高校の文化祭向け「うちちみくじ」Webサイトの作成

## 1. 目的
高校の文化祭で利用する、おみくじ形式のWebサイトを作成してください。

スマートフォンでの利用を前提とし、来場者が簡単な操作でおみくじを引き、結果を楽しめるサイトを目指します。

公開先は **GitHub Pages** とします。そのため、GitHub Pagesで動作しないサーバー機能やバックエンド処理は実装しないでください。

## 2. 技術的な制約
- GitHub Pagesで公開・実行できる静的Webサイトとして実装する。
- HTML、CSS、JavaScriptを基本とする。
- 必要に応じて、既存プロジェクトで使用しているライブラリを利用してもよい。
- サーバーサイド処理、データベース、独自API、バックエンドサーバーを必要とする機能は実装しない。
- 画像などの静的ファイルは、リポジトリ内に配置して参照できるようにする。
- GitHub Pagesのサブパスで公開される場合も考慮し、画像やCSSなどのパスを適切に設定する。
- スマートフォンの縦画面を優先し、PCでもレイアウトが崩れないようにする。

## 3. サイトの基本仕様

サイトは、次の3段階で構成します。

### 画面1：トップ画面
表示内容：
- 「うちちみくじ」というタイトル
- おみくじを引くことを促す短い説明文
- 「おみくじを引く」ボタン

要件：
- 初めてアクセスしたときに表示する。
- ボタンはスマートフォンでも押しやすい大きさにする。
- ボタンを押すと、おみくじの演出画面に切り替える。
- ボタンの連打によって演出や抽選が重複しないようにする。

### 画面2：おみくじの演出画面
おみくじの結果を表示する前に、抽選を盛り上げる演出を行います。

要件：
- ボタンを押したことが視覚的に分かる演出を実装する。
- CSSアニメーションやJavaScriptによる演出を使用する。
- 演出中であることが分かる表示を用意してもよい。
- 演出の終了後、自動的に結果画面へ切り替える。
- 演出時間は長くなりすぎないようにする。
- 演出中は追加の抽選操作を受け付けない。
- JavaScriptのみで実現できる範囲とし、外部サーバーに依存しない。

### 画面3：おみくじの結果画面
表示内容：
1. おみくじの結果に対応する画像
2. 画像の下に表示する結果の文章
3. 「もう一度引く」ボタン

要件：
- 画面中央を基準に、画像を見やすく表示する。
- 画像の縦横比を維持し、画面からはみ出さないようにする。
- 画像の下に、結果に対応する文章を表示する。
- 文章が長い場合でも、スマートフォンで読みやすいレイアウトにする。
- 「もう一度引く」ボタンを結果の文章の下に配置する。
- ボタンを押すと、再び演出画面に切り替わり、新しい抽選を行う。
- 結果画面でもトップ画面へ戻らず、繰り返しおみくじを引けるようにする。

## 4. 抽選の仕様

おみくじの結果は、あらかじめ定義した結果データからランダムに1つ選択してください。

各結果は、少なくとも次の情報を持つものとします。

- 結果を識別するID
- 表示する画像のパス
- 表示する文章

要件：
- 抽選処理はクライアント側のJavaScriptで実行する。
- 画像と文章は、必ず同じ結果データから取得する。
- 画像と文章の組み合わせが食い違わないようにする。
- 結果の追加や変更が容易な構造にする。
- 特定の画像を表示する対象範囲は、コード内で明確に定義する。
- 抽選対象の画像や文章が存在しない場合に、画面が壊れないようにする。

なお、結果の種類・画像の保存場所・各結果の文章については、既存プロジェクトの内容を確認してから決定してください。未確定の内容を勝手に確定せず、必要な場合は仮データであることを明示してください。

## 5. デザイン・操作性
- スマートフォンでの操作性を最優先する。
- 画面幅に応じてレイアウトを調整する。
- タイトル、説明文、画像、結果文章、ボタンの視認性を確保する。
- ボタンはタップしやすい大きさと間隔にする。
- 抽選中、結果表示中など、現在の状態が分かるようにする。
- アニメーションを過度に複雑にせず、一般的なスマートフォンで滑らかに動作するようにする。
- 画像の読み込みに失敗した場合も、文章や再抽選ボタンが利用できるようにする。
- アニメーションを減らす設定の利用者にも配慮する。

## 6. 開発時のルール
作業を始める前に、既存プロジェクトの構成と実装を調査してください。

- 既存ファイルを確認し、現在の画面構成と関連するコードを把握する。
- 既存の仕様やデザインを必要以上に変更しない。
- 変更するファイルと変更理由を明確にする。
- 作業前に実装方針を提示する。
- 不明点や重大な仕様変更が必要な場合は、実装前に確認する。
- 調査段階ではファイルを変更しない。
- 承認を得てから実装に進む。
- 承認前にファイルの変更、テストの追加、テストの実行を行わない。
- 既存のテストや設定を削除・上書きしない。
- 実装後は変更内容を説明し、テスト結果を報告する。

## 7. テスト項目
実装後、可能な範囲で以下を確認してください。

1. 初回アクセス時にトップ画面が表示される。
2. おみくじボタンを押すと演出が始まる。
3. 演出終了後に結果画面が表示される。
4. 抽選結果に対応した画像と文章が表示される。
5. もう一度引くボタンから再抽選できる。
6. 連続操作によって抽選処理が重複しない。
7. 画像が存在しない場合でも、文章と再抽選ボタンが利用できる。
8. スマートフォン相当の画面幅でレイアウトが崩れない。
9. コンソールに予期しないJavaScriptエラーが発生しない。
10. GitHub Pagesへの公開を想定したパスで静的ファイルを参照できる。

ブラウザテストが利用できる場合は、Playwrightなどを使用してください。利用できない場合は、実行できなかったテストとその理由を明示してください。

## 8. 完了条件
以下を満たした時点で完成とします。

- トップ画面、演出画面、結果画面が仕様どおりに動作する。
- 抽選結果と画像・文章の対応が正しい。
- 再抽選が正常に動作する。
- スマートフォンで操作できる。
- GitHub Pagesでの公開を前提とした静的構成になっている。
- 実施したテストと未確認事項が報告されている。

まずは既存プロジェクトを調査し、変更予定のファイル、実装方針、テスト方針を提示してください。この段階ではファイルを変更せず、私の承認を待ってください。
